# Chess: no game of a person against an engine and no analysis; the engine opponent exists in `src/Chess/Engine/` but nothing in the game uses it

**Where:** `src/Chess/Game/ChessGameModel.h` (`OnSquareClicked` is the path of a person, `TryMove` the path of anything else; the model has no notion of a side played by a program), `src/Chess/Components/` (the board, the pieces and the result bar), `src/Chess/Game/Position.h` (`DoMove` / `UndoMove` exist), `src/Chess/Engine/` (the opponent core, see item 2: nothing calls it), `tools/stockfish_bridge.py` (the only way a whole game is played against Stockfish today), `engine/src/Modules/TaskSystem/` (a search runs off the main thread).

**What is missing** (found by reading the code and searching `src` and `tools`, not by playing):

1. A person cannot play the computer: both sides of the game are mouse clicks. The core of an opponent exists on this branch (item 2) but nothing connects it to the window, so a whole game against Stockfish is still played only through `tools/stockfish_bridge.py`, which needs the control API switched on, Python and an installed Stockfish, and a person at the window on the real clock (not tried yet, see the control entry (engine entry `control-api-gaps`)). It is a test and development tool, not a feature of the game.
2. **What exists** (this branch, `src/Chess/Engine/`, covered by `ChessTests`): the interface `IChessEngine::FindMove(SearchRequest, CancellationToken)` (the request is the start FEN, the moves and the limits; errors are `EngineError` values), a UCI client over a POSIX child process (`UciProcess`, `UciEngine`: handshake, timeouts, `stop`, a new process after an error; `FindStockfish` looks for a path, nothing is shipped), the asynchronous driver `EngineOpponent` (it plays one side of a `ChessGameModel`: `Update` on the main thread starts the search on the `TaskManager` Background pool and plays the answer with `TryMove`; stale answers are dropped by `GetVersion()`), and gtests against a fake UCI engine (`tests/fake_uci_engine.py`) that need no Stockfish, plus `UciEngineStockfishTest`, which skips itself without one. **What is still missing:** no component or `ChessGame` creates or updates an `EngineOpponent`; no setting or file picker for the engine path, the side or the strength; no UI (the opponent is thinking, the engine failed, a new game with a side); no Windows process code (`UciProcess::Start` answers `Unsupported` there), and the web target and Android cannot start a process; no opponent state in the control API (`ChessGameControl`); no engine of our own. Stockfish is GPL-3.0 and the repository has no license file, so what linking or shipping it would require is not settled; the game only starts a copy the user installed. An engine for the web target has to run in the game's own process.
3. There is no analysis of any kind: no evaluation, best move or lines, no move list on the screen, no takeback, no stepping through the game, no resign or draw offer, no clocks, no PGN. The model keeps `GetStartFen()` and `GetMoves()`, which are enough to rebuild any earlier position, and `Position::UndoMove()` exists, but no player action uses them. The engine can draw text now (`TextComponent`, `BECore/Text/CLAUDE.md`), but there is no in-game UI to lay out a move list, a number or an opening name (No in-game UI (engine entry `in-game-ui`)).
4. The choices a person needs have no place to live: which side to play, the strength of the opponent, a new game, resign, and the piece of a promotion (a click on the last rank always plays the queen; the other pieces are reachable only through `TryMove` and UCI).

**Decided by the owner (2026-11-03), the opponent:**

1. An abstract engine interface in the game (`src/`) ("a move for this `Position` within this time or strength") that runs the search off the main thread through `TaskManager` and plays the answer with `TryMove` on the main thread, so the model and the scene stay as they are.
2. First implementation: Stockfish as a separate child process over UCI (the logic of `UciEngine` in `tools/stockfish_bridge.py` ported to C++), the path chosen by the user, nothing shipped. This keeps GPL-3.0 code out of the game and out of `engine/` (other games of the engine may be sold; GPL code must never enter `engine/`). It works on desktop only: the web target cannot start a process and Android only in ways an app should not rely on.
3. Later, behind the same interface: an engine of our own in `src/` (alpha-beta over the existing `MoveGenerator`), in the game's process on every target and deterministic for a fixed depth (the manual clock and the smoke tests need that). Linking Stockfish in is not planned.

**A fix has to cover** (the rest is a direction to confirm with the owner, not a decision):

- **the opponent:** as decided above;
- **the controls of a game:** side, strength, new game, resign, takeback (rebuild from `startFen` + `moves`, or `UndoMove`) and the promotion choice, on the in-game UI and the text of the roadmap entries; the opponent's turn is shown (the game must not look frozen while it thinks);
- **analysis** (needs the UCI engine of (a) for anything deeper than a basic evaluation of our own): an evaluation bar and a best-move hint after each move; a move list that can be clicked to view an earlier position without changing the game; a review after the game that evaluates every position in the background and marks the moves that lost the most; PGN export and import; opening names from a table. `MultiPV` and `go depth` give the lines;
- **the control API and tests:** the opponent as state of `ChessGameControl` (its side and strength, and "thinking" in `get_state`), so a model can play a game against the engine of the game itself; gtests of the engine on known positions (a mate in one and two, a hanging queen, a draw by repetition); a smoke scenario of a whole game against it; `stockfish_bridge.py` stays as the independent referee of the rules and as the yardstick for the strength of our own engine (a match of a fixed number of games at a low `Skill Level`).
