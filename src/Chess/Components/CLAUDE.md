# Chess scene and UI (src/Chess/Components, config/SceneConfig.xml, config/nodes/)

Read this before changing `config/SceneConfig.xml` or a file of `config/nodes/` (which file holds which node: `config/CLAUDE.md`). Siblings: the opponent `src/Chess/Engine/CLAUDE.md`, the rules `src/Chess/Game/CLAUDE.md`, the tests `tests/CLAUDE.md`. Components keep no game state: everything is read from the model (`ChessGame::GetActiveModel()`) on every update or draw.

## Files

```
ChessBoardComponent     the board: squares, highlights and coordinates, clicks and drags, the frame (the opponent's, the analyst's and the draw judge's Update() every SceneUpdateEvent, the keeper, the result log)
ChessHudComponent       on Hud, before its canvas: publishes the UIVars of the HUD and the opponent panel in its draw, answers ChessReset
ChessMenuComponent      on MenuPanel: ChessOpenMenu, ChessOpenSection, ChessCloseMenu
ChessOpponentPanelComponent  on OpponentPanel, before its canvas: ChessSet*, the Stockfish segment
ChessPromotionPanelComponent on PromotionPanel, before its canvas: shown while a promotion is pending, ChessPromote, ChessCancelPromotion
ChessMaterialComponent  on the node Material, before its canvas: icons, the material... variables, which set (margin or move panel) and which rows are shown
ChessMovePanelComponent on the node MovePanel, before its canvas: the variables of the move list rows, rows and marks shown or hidden, the box shown where it fits; ChessShowMove, ChessTakeBack
ChessMovesSectionComponent on the node MovesSection (the menu section "Moves"), before its canvas: the same variables, its own rows and marks
MoveRows                the part both share: the rows of the game (CurrentMovePanelRows), the words (PublishMovePanelWords), the rows and marks of one canvas (MoveRowsOnCanvas), the takeback (TakeBackPliesNow, TakeBackOnCanvas)
ChessPieceComponent     one piece node: follows its piece in the model, slides a played move, switches its sprite after a promotion
ChessResultComponent    its own node (layer 1): dims the board and draws the result bar once the game is over
```

**Each UI node answers its own actions** with a component of its own; the board knows only the picker (`ChessPromotionPanelComponent::SyncActive()` after a click, since the order in which two components get one event is not defined). **A new panel** is a node file with its own component and its own `tests/ChessUi<Topic>Test.cpp`, no change to the board. The frame: the board's update lets the program move, then the HUD publishes in its draw (a test holds it).

## The board

- **Four views** (`viewVariants` of `ChessScene`): the default 840 x 800, `Tall` 720 x 1204 (`maxAspect:0.59`, listed first: the first variant that holds wins), `Portrait` 720 x 960 (`maxAspect:0.875`: the view whose board is bigger on the screen; a square window keeps the default) and `Wide` 1120 x 800 (`minAspect:1.4`). The board is 640 x 640 in all (a square 80 units), at (100, 80) in the default and Wide view and (40, 144) in Portrait and Tall. **The one rule: a view is widened or heightened only where the other side already limits the view it replaces**: Wide and Tall never shrink a board, font or touch target; the letterbox they take is the move panel's. Tall is Portrait with 244 units more at the bottom, every place of Portrait kept (`HasPortraitPlaces()`). A canvas lays out per view with a variant `orientation:portrait` (conditioned on the canvas's bounds, the view in units; it holds in Tall too); Wide needs no variant, the HUD's anchors move its right end.
- **Geometry** is in scene units of the active view: `_originX/_originY/_squareSize` (default and Wide) and `_portraitOriginX/_portraitOriginY/_portraitSquareSize` (Portrait and Tall); change a pair with the numbers of the canvases around it. The component takes one set on `SceneViewChangedEvent` (`HasPortraitPlaces(name)`) and every accessor reads that choice, so the squares, the pieces and the result bar cannot disagree for a frame; a drag in the hand ends with the view. The board is not a named region. The mouse goes through `Scene::ScreenToSceneX/Y`.
- **Orientation:** the board is drawn from Black's side exactly when the program plays White (`BottomColor(OpponentController::GetPlays())`, read live on every use). `SquareToPixel` and `OnMouseDown` map through `Game/BoardOrientation.h`; everything placed on a square uses them. The HUD, panels, model, control API and FEN do not turn.
- **Coordinates:** 16 labels of a `SceneView` canvas on `BoardCoordinates` (layer -1, after `Board`, no safe area, no `blocksInput`). The rects are fixed per view (a variant sets each label for the Portrait origin), the text (`coordRank<row>`, `coordFile<column>` from `Game/BoardCoordinates.h`) turns. A turn keeps the parity of the grid, so the label colors are static; `IsLightSquare` is the one function for it.
- `ChessOpponentPanelComponent` shows the segment `EngineStockfish` exactly while `OpponentController::OffersStockfish()` (a **cached** answer, no file lookup per frame; `RefreshStockfish()` looks again when the opponent section opens, so a Stockfish installed meanwhile shows up then). The scene file is the same everywhere.

## Highlights

Order inside the board's `OnDraw()`: squares, the last move (`kLastMoveSquare`, from and to of `GetMoves().back()`; castling marks the king only), the check (`kMateSquare` once over), the hint (`kHintFromSquare` / `kHintToSquare`, while `PositionAnalyst::GetHint(model)` has one and the game is not over), the premoves (`kPremoveSquare`), then the selection and its legal targets last so they stay readable. Each has a hue of its own. Nothing is kept: a move, reset or `set_state` takes a mark off at the next draw. **While an earlier position is viewed** (`ChessGameModel::IsViewing()`) the marks are those of `GetShownPosition()` (its move, its check), with no hint, premove, selection or result dim; a press on the board only ends the view, also in a finished game.

## The pieces

- A piece node is a reference of the prefab `config/nodes/ChessPiece.xml` (`name`, `spriteId`, `file`, `rank` overridden); a new piece node is another such reference. The prefab is `ChessPieceComponent` + `SpriteRendererComponent` + `TransformComponent`, the node the whole square and the sprite `fit="Contain"` (the atlas `assets/chess_test.png` must keep its alpha). A piece registering late is dealt to the position as it stands.
- A piece stands on `GetShownSquareOf()`: the viewed position's square while viewing; a view that begins or ends places the pieces at once.
- **A played move slides** (`ScopedTween`, `_slideDuration`, reflected, not set in the scene). Only a change of exactly one move and one version with time in the frame slides; everything else snaps (first sighting, reset, `set_state`, several moves at once), and a frame with `deltaTime` 0 snaps, so UI tests need no waiting. A captured piece leaves when the slide ends.

## The premove

While the program thinks and the person has the other color, `OnMouseDown` hands the click to `ChessGameModel::OnPremoveClicked` (the queue and its rules: `src/Chess/Game/CLAUDE.md`): an own piece selects, a target queues, any other click drops the whole queue. No drag, no promotion panel: a premoved promotion plays a queen. While two programs play the board ignores clicks.

## The drag

`ChessBoardComponent` only; the model knows nothing. The press acts at once (a click). A left press on the square the model has selected, with the game on and no promotion pending, arms a drag; past `kDragThreshold` it is lifted. A release over a legal target calls `OnSquareClicked(target)`; anywhere else nothing is called, so the piece stays selected (and a release on another own piece does not select it, the owner's decision). `IsDragValid` drops it silently when the model moves under it. While lifted `GetLiftedPiece()` places the piece under the pointer on `kDragLayer` (6: over pieces, result and material, under HUD and panels). A dropped move snaps; the program's reply slides.

## The promotion picker

A click on a promotion target leaves it pending in the model; the node `PromotionPanel` (`ChessPromotionPanel.xml`, modal `SceneView` canvas, layer 20, `visible="false"`) is shown by `ChessPromotionPanelComponent` exactly while `HasPendingPromotion()`, checked after a click and every update and draw, so a reset, `set_state` or someone's move closes a stale one. Buttons `PromoteQueen` .. `PromoteKnight` (`ChessPromote`, the id from `Game/PromotionChoices.*` as `value`) and `PromotionCancel` (`ChessCancelPromotion`: the pawn stays selected); `PromotionDim` cancels too. Element names start with `Promotion` or `Promote`.

## The captured material

Node `Material` (`ChessMaterial.xml`, layer 5, after `BoardCoordinates`): `ChessMaterialComponent`, then a `SceneView` canvas (no safe area, not modal). Two groups mirrored about the board's middle (in Portrait two rows, above and below the board), `MaterialTop*` and `MaterialBottom*`, each a balance label and five rows (icon + count `{material<Top|Bottom><Type>}`); every name starts with `Material`. The variables are written only when the model, its version or the bottom color changed.

- The lower group is what the color at the bottom has taken (its icons are the other color's); the groups swap when the board turns. The balance (`BalanceText`, "+N" for the side ahead) is the difference on the board (`Game/CapturedMaterial.h`).
- A row shows when its count is above 0 and `MaterialListFits` (the box of the active view, `Game/MaterialLayout.h`, inside the canvas's `safeBounds`, in view units); nothing shows before the first layout. With side insets (the narrowest window of either view) the lists hide and the balance stays (the owner's decision).
- **In the move panel** (the owner's decision): the canvas has a second set of both groups, `MaterialPanel*` (horizontal lists of 52-unit chips and a balance), over the panel's bands `MovePanelBandTopPlayer` (the upper group) and `MovePanelBandBottomPlayer` (the lower one), bound to the same variables, its icons given the same sprites. The component shows **exactly one set**, whole: the panel set while `MovePanelFits` holds for the Wide box and the canvas's `safeBounds` (so the material is in the panel exactly while the Wide panel is shown), the margin set otherwise and before the first layout (default, Portrait and Tall view, a Wide window whose side insets cut the panel; the Tall panel has no player bands). The panel set has no fit rule of its own: the box lies in the safe area whenever it is shown. The Wide view's left margin is then empty; the board keeps its place.
- **Known limits:** a "+39" beside a rank "8" may read as one number; with a top notch `Turn` (layer 10) covers the upper group's first rows and its balance (in Portrait only where the view fills the window, a 3:4 one; Tall is low enough to leave 9:16 a bar that takes the notch), which a test asserts; moving the group breaks the mirror, so the fix is the owner's call. In the panel a top notch (a case of the size matrix, not of a phone held sideways, which has side insets) puts `Menu` and `Reset` over the right part of the upper group and its balance; the first chips stay clear (a test pins it).

## The move panel

Node `MovePanel` (`ChessMovePanel.xml`, layer 4, under `Material`, which draws over its bands): `ChessMovePanelComponent`, then a `SceneView` canvas (no safe area, not modal) with one root `MovePanelBox`, the plate right of the board in the **Wide view** (the box of `Game/MovePanel.h`): top down the band `MovePanelBandTopPlayer`, 8 rows of 56 units (`MovePanelRow<i>`: a number and a White and a Black cell, the cell of the last move shows its gold `...Mark<i>` under the text), the band `MovePanelBandBottomPlayer` and the band `MovePanelBandButtons` (the step buttons). The players' bands are empty: `Material` draws over them ("The captured material"; a test holds both files to the same bands). There is no title; every name starts with `MovePanel`. The 8 rows are two columns of four (`MovePanelColumn0/1`), one under the other in Wide; **in the Tall view** a variant of the canvas (`maxAspect:0.6`, which only Tall's bounds meet) puts the box under the board and the lower material row, hides the two player bands (the material keeps its Portrait rows there) and sets the columns side by side; the band of the buttons stays under the list.

- The component (with `MoveRows`) rebuilds `BuildMoveList` and `BuildMovePanelRows` only when the model, its version or its shown move count changed (`MoveRowsKey`; a view moves no version), writes the `movePanel*<i>` words of the 8 rows and shows the rows and marks the entries say; the rows are the **page** of the shown move (the engine's UI has no scroll: `Game/MovePanel.h`), its cell marked.
- **Where it is hidden:** `MovePanelBox` is shown only while `MovePanelFits` holds for the box of the active view (`MovePanelView`: Tall for `Tall`, else Wide) and the canvas's `safeBounds`, asked on every draw and never before the first layout. The default and Portrait views hold neither box; side insets cut it in the narrowest Wide windows (3:2 and 16:10 keep it) and in every Tall window. Those windows have the menu section `Moves`: node `MovesSection` (`ChessMovesSection.xml`, layer 20, modal), built like the opponent panel, with the same 8 rows bound to the same variables (its component writes them too) and the same step buttons; it is in the menu in every window and stays open while it views.
- **Clicks (viewing):** the cells of the moves and the step buttons `‹` `›` `»` (`<prefix>StepBack`, `StepForward`, `Latest`: 56 x 56 at the left of the buttons band) are buttons of one action `ChessShowMove`, its `value` the press of `Game/MovePanel.h` (`white<i>`, `black<i>`, `back`, `forward`, `latest`); `ChessMovePanelComponent` answers it for both canvases (their rows are the same) with `ChessGameModel::ShowMoves`. The cell of the last move and `»` return to the game, so do a press on the board and any change of the game.
- **Take back** (`<prefix>TakeBack`, the rest of the band): action `ChessTakeBack`, answered by `ChessMovePanelComponent` for both canvases with `TakeBack(TakeBackPliesNow())` (`Game/TakeBack.h`); each canvas's component greys its own (clicker `disabled`) while that is 0. While viewing it ends the view and takes back from the game's last move. Nothing else in either list takes a click.
- **Known limit:** the HUD follows the safe area, the box does not. A notch (7 % of the short side) pushes `Menu` and `Reset` down onto the top band; the rows and the two lower bands are clear of the HUD in every window (`ChessUiTest` pins which controls come closer than 8 units, per band and kind of window). The home bar of side insets (4 %) lifts `Status`, so in the Wide view a variant of `ChessHud.xml` makes it 38 units high on the safe edge: never over the box (the owner's rule).

## The HUD

`SceneView` canvas on `Hud` (`ChessHud.xml`, layer 10), controls 56 units high in the margins: `Turn` (`{turn}`), `Menu` (fixed word, `ChessOpenMenu`; the owner wants no button named after a state, and no element is called `Opponent`), `Reset` (`ChessReset`), `Status` (`{status}`; wider in Portrait). The anchors keep the top row above the board and `Status` under it in every view (in Wide, `Menu`, `Reset` and `Status` are at the right end, over and under the move panel's box; `Status` lower there, "The move panel"). The widest sentences only just fit the narrowest window (480 px with insets): a longer one needs a reword or a wider box; an error says what went wrong, never what to do. `ChessUiTest` holds the layout on the matrix with every word of `tests/HudWords.h`, `ChessHudWebTest` the HTML twin of the default view's HUD (no Portrait twin).

`ChessHudComponent` republishes the variables when the model's version, the controller's revision, the draw judge's revision, `IsThinking()`, the person's color or the view changed: `turn` (`StatusText::Turn`, "Computer is thinking", also while the draw judge is `Pending`), `status` (while viewing `StatusText::Viewing`, over all; else a standing error of the opponent; else "Draw declined" while the judge shows `Declined` for the model's version; else the game status, "Check" included), `opponentError`, and the panel bindings `opponentMode`, `opponentColor` (**the person's** color), `opponentEngine`, `opponentLevel`.

## The menu

Node `MenuPanel` (`ChessMenuPanel.xml`, layer 20, modal, `visible="false"`): `MenuDim`, `MenuPlate`, `MenuTitle`, one 56-unit button `MenuSection<Name>` per section (`ChessOpenSection`, the section id as `value`) and `MenuClose`; names start with `Menu`. `ChessOpenMenu` shows the list and hides every section, `ChessOpenSection` swaps the list for the section's canvas (an unknown id logs one warning), `ChessCloseMenu` hides all. `MenuDim` is a button of its own with the action of `MenuClose`, so a click beside the plate closes the list; the same holds for `Dim` of the opponent panel and `PromotionDim` of the promotion picker, each with `stateLook="false"` (no hover look) and always the first child of its canvas, so a click on a plate is hit first and never reaches it. Escape is not wired. The sections are the table `Game/MenuSections.*`. The menu is no state. The sections are `Opponent` and `Moves` ("The move panel"). **A new section** is a table row, a button, its own panel with `Back` and `Close`, and 68 units more in `MenuPlate`; a test fails a button without a row and the reverse.

## The opponent panel

Node `OpponentPanel` (`ChessOpponentPanel.xml`, layer 20, modal, `visible="false"`), after the engine's choice-panel template (`engine/src/Modules/BECore/UI/CLAUDE.md`, "Choice panels"): `Dim` (a click on it closes the panel, as in "The menu"), `Plate`, four `UISegmented` rows with the control API ids as segment values, `ModeGroup` (`opponentMode`, `ChessSetMode`), `ColorGroup` (`opponentColor`, `ChessSetColor`), `EngineGroup` (`ChessSetEngine`), `LevelGroup` (`ChessSetLevel`), the `OpponentError` line and `OpponentBack` / `OpponentClose`. A segment needs an explicit `height`. The modal panels are centered plates (94% of the safe area up to 640) and fit every view; only this one has a Portrait variant (the plate takes the whole safe area and the captions get narrower), for the 590 safe units of the narrowest Portrait window. A test lists the canvases of the scene and fails for one with no matrix test over the views.

- The group owns no choice: a press emits the action, `ChessOpponentPanelComponent` picks through `ChessGame::GetActiveChoice()` and `ChessHudComponent` publishes the variable, so the panel shows what the game has. An id in no table logs one warning.
- **The color is the person's**; `opponent.plays` of the control API is the program's.
- A pick applies at once and the panel stays open. No group is greyed (a disabled group read as a dead button): a pick made while two people play is kept and applies when Computer is picked.
- A refused pick changes nothing (no fallback, the program is not switched off); "Engine not found" stays in `OpponentError` and `Status` until someone's move, a reset, `set_state` or the next pick. The panel never offers a Stockfish that is not found.
- No name may be in two canvases, hence `ModeGroup`, not `Mode`.

## Draw order

By layer, not by place among the references of `SceneConfig.xml` (`engine/src/Modules/BECore/Scene/CLAUDE.md`, "Draw order"); the same layer draws in scene order. `Board` and then `BoardCoordinates` -1, pieces 0, `Result` 1, `MovePanel` 4, `Material` 5, a dragged piece 6, `Hud` 10, the panels and the menu 20. A test reads the draw calls of one frame.

## Allocations

A steady frame of the scene allocates nothing on the main thread in any state a game sits in; `ChessUiAllocTest` pins it in a profile build (`ENGINE_PROFILER_ALLOC`), and a frame that changes something (a move, the start of a search) does allocate.
