# Chess Module Guidelines

## Overview

`ChessGame` is an `IGame` (name `Chess`, scene `ChessScene`). Executable `BagiChess`. Infrastructure and how a game is registered: `engine/src/Modules/Games/CLAUDE.md`. Namespace `BECore::Chess`. The game's content is in `config/` (`ApplicationConfig.xml`, `SceneConfig.xml`, `TextureLibrary.xml`, `ChessSettings.xml`) and `assets/`. `BagiChess` starts in Game mode (`mode="Game"` in its `ApplicationConfig.xml`, no editor); set `mode="Editor"` to open it in the scene editor.

## Layout

```
src/Chess/
├── ChessGame.{h,cpp}         IGame; owns the shared ChessGameModel, the OpponentController, the OpponentChoice over it, the PositionAnalyst (evaluation and hint, off at the start) and the control adapter; Start() resets the model, loads OpponentSettings, starts with nobody as the opponent and Stockfish as the engine and forgets the person's color (White), Reset() resets the model, Stop() destroys the opponent and shuts the analyst down; GetActive() / GetActiveModel() / GetActiveOpponent() / GetActiveChoice() / GetActiveAnalyst() are how components reach them
├── ChessGameControl.{h,cpp}  IControllableGame: the state, the legal moves, a way to play one, to load a FEN and to pick the computer opponent and to switch the analysis for the control API (below); holds the model, the `OpponentController` and the `PositionAnalyst`
├── Game/                     plain C++ rules, no scene or renderer (src/Chess/Game/CLAUDE.md)
│   ├── ChessTypes.h, Bitboard.h, Move.h, Attacks.*   squares, pieces, bitboards, moves, attack tables and magics
│   ├── Position.*, MoveGenerator.*, GameStatus.*      position and FEN, legal moves and UCI, mate / stalemate / draws
│   ├── ChessGameModel.*      the state of the game: selection, moves, history, version, piece handles, pending promotion
│   └── StatusText.*, BoardOrientation.h, BoardCoordinates.h, PromotionChoices.*, CapturedMaterial.*, MaterialLayout.h   pure helpers of the UI
├── Engine/                   the computer opponent (src/Chess/Engine/CLAUDE.md)
│   ├── ChessEngine.h, Analysis.*, SearchRequest.*     IChessEngine (FindMove, Analyse), the request and the analysis
│   ├── UciProtocol.*, UciProcess.*, UciEngine.*       Stockfish over UCI in a child process (POSIX)
│   ├── Evaluation.*, Search.*, TranspositionTable.*, OwnEngine.*   the engine of our own
│   ├── BlunderEngine.*, OpponentLevels.*, OpponentEngines.*, OpponentText.*, OpponentSettings.*   handicap, levels, engines, words, settings
│   ├── EngineOpponent.*, OpponentController.*, OpponentChoice.*   the opponent in a game, its seat, the person's choice
│   ├── PositionAnalyst.*     the analysis of the position in the background: the evaluation and the hint (one `Analyse` per version), the hint rule `HintRefusalFor`, `MakeAnalysisEngine`; owns the `MoveRater`
│   ├── AnalysisEngineFactory.h   the type of the factory of an analysis engine, shared by `PositionAnalyst` and `MoveRater`
│   └── MoveRating.*, MoveRater.*   the rating of the played moves: `MoveRating` is the pure rule (a move is brilliant when it is the engine's best move and it was a choice), `MoveRater` rates a game in the background with the own engine at depth 5
├── Uci/                      the own engine as a UCI program, the server side: `BagiChessUci` (`uci/main.cpp`), command parser, clock rule, `UciServer`; no game, no scene (src/Chess/Uci/CLAUDE.md)
└── Components/               scene glue: board, hint, pieces, result, captured material (src/Chess/Components/CLAUDE.md)
```

- State lives in `ChessGameModel`. Components never keep game state: they reach the model through `ChessGame::GetActiveModel()` (null when Chess is not the active game, and then they do nothing).

**Where the details are** (each file loads when a session works in its folder; read the matching one before changing code there):

| File | Holds |
|------|-------|
| `src/Chess/Game/CLAUDE.md` | every file of the rules and what it guarantees |
| `src/Chess/Engine/CLAUDE.md` | the opponent: the engine interface, UCI and Stockfish, the own engine, the levels and the handicap, the settings file, the controller and the choice, the opponent in the running game |
| `src/Chess/Uci/CLAUDE.md` | `BagiChessUci`, the own engine speaking UCI on stdin / stdout: the files, the commands and options, the `stop` rule, the clock rule, how to run it and its smoke |
| `src/Chess/Components/CLAUDE.md` | the scene and the UI: the pieces, the board geometry and orientation, the hint on the board, the coordinates, the captured material, the HUD, the opponent panel, the promotion picker, the words of the HUD, the draw order; **read it before changing `config/SceneConfig.xml`** |
| `tests/CLAUDE.md` | every test file and what it covers, the control smoke, the fake UCI engine, the test helpers |

## Control API

`ChessGame::AsControllable()` hands out `ChessGameControl` (`engine/src/Modules/Games/CLAUDE.md` for the methods and the rules of an adapter). The model and the opponent controller belong to the game, so the adapter holds references and has no `no_active_model`. The wire format is in the header comment of `ChessGameControl.h`; in short:

| Method | What it does |
|--------|--------------|
| `get_state` | `{fen, board, turn, status, winner, inCheck, legalMoveCount, startFen, moves, opponent, material, analysis}`: `board` is 8 strings, rank 8 first, white upper case, `.` empty; `status` is `ongoing`, `checkmate`, `stalemate`, `draw_insufficient_material`, `draw_threefold` or `draw_fifty_moves`; `startFen` plus `moves` (UCI) rebuild the game with its repetitions; `material` is `{balance, capturedByWhite, capturedByBlack}` (below); `analysis` is the evaluation, the hint and the ratings of the moves (below); `opponent` is `{plays, level, engine, seats, thinking, error}`: `plays` the color the **program** plays (`"white"`, `"black"`, `"both"` while two programs play each other, or `null` for two people, the start of every game), `level` the id of the strength (`easy`, `medium`, `hard`, `max`; the one that would be used, also while `plays` is null), `engine` the id of the program (`stockfish`, the start of every game, or `own`; also the one that would be used while `plays` is null); `level` and `engine` are those of the seat that plays when exactly one plays, else White's; `seats` is `{"white": {engine, level}, "black": {engine, level}}`, always present (the choice per color, also for a color nobody plays); `thinking` whether a search of either program runs, `error` `null` or `{kind, detail}` (`kind` in snake_case: `launch_failed`, `timeout`, `process_died`, `protocol_error`, `illegal_move`, `no_move`, `bad_request`, `cancelled`, `unsupported`; `detail` the sentence of the log). A pick of Stockfish succeeds whenever a Stockfish file is found, so a launch that fails shows only at the first search, as `error` `launch_failed`; a pick of `own` always succeeds |
| `list_actions` | `{"type": "move", "uci": "e2e4"}` for every legal move (a promotion is four); empty once the game is over |
| `perform_action` | plays one of them and answers `{move, status, turn, winner, inCheck}`; errors `illegal_action`, `promotion_required` (`e7e8` without the piece), `game_over`, `invalid_params` (not a UCI move) |
| `reset` | the opening position; takes no options; **keeps the opponent** (side, level and engine; a standing error goes by the version rule) |
| `set_state` | `{"fen": ".."}` and/or `{"opponent": {"plays": "white"\|"black"\|"both"\|null, "level": "easy"\|"medium"\|"hard"\|"max", "engine": "stockfish"\|"own", "white": {"engine", "level"}, "black": {..}}}` (inside `opponent` a missing member means unchanged, per seat; `{}` changes nothing). `level` and `engine` set **both** seats (the old shape, which keeps every meaning); the seat objects `white` / `black` (an object with the optional members `engine` and `level`; anything else in it is `invalid_params`) then override one seat; then `plays` says who plays, and a missing `plays` keeps the sides as they are. `"both"` starts a game of two programs (an engine object per seat, never shared; the pace and the pause are slice 2 of the entry `chess-computer-vs-computer`); `plays: "white"` while both play is a takeover (the person has Black; White's program and its search stay), `null` ends it. A FEN starts a game from any position `FromFen` accepts, finished ones included (the pieces in the scene are dealt out again, `SetPosition`). None of `fen`, `opponent`, `analysis`, a side that is not `white` / `black` / `both` / null (`"Both"`, `""`, a number), an unknown level, an engine that is not exactly `stockfish` or `own` (`"Own"`, `""`, null, a number), a member of the wrong type: `invalid_params`, and nothing is changed (everything is checked first). The opponent is applied first, then the position. No engine for the pick (no Stockfish found; only Stockfish can fail, in either seat): `engine_unavailable` with the engine's sentence; the pick is **refused as a whole** (all or nothing: every seat that is new or changed is asked first, the new choice of a seat that is fine is not applied either): the position is **not** replaced and the opponent is **unchanged** (sides, seats, level, engine and a running search stay as they were, also when the program played before: a client that asks for stockfish while `own` plays as black gets `engine_unavailable` and `own` still plays black; the level of a refused pick is not saved either, so `{"opponent": {"engine": "own", "plays": "black"}}` is the way on from two people) and `opponent.error` has the reason (until the version moves by someone else or the next pick; before this change the program played nobody after a refusal). A pick that changes nothing does nothing (no restart, no new version); `plays: null` clears an error. `{"analysis": {"evaluation": bool, "hint": bool, "ratings": bool}}` switches the evaluation, asks for or drops a hint and switches the rating of the moves (below; `ratings` has no refusal, a finished game may be switched); it **cannot be combined with `fen` or `opponent`** in one call (`invalid_params`; two calls say it plainly), a wrong type or an unknown member is `invalid_params` and nothing is changed; a hint on a side that the program plays is `not_your_turn` (so on either turn while two programs play), on a finished game `game_over` (the evaluation switch of the same call is not applied either) |

- `material` is `{"balance": int, "capturedByWhite": {"queen", "rook", "bishop", "knight", "pawn"}, "capturedByBlack": {...}}`, a counts-per-type object for each side. `balance` is White's points minus Black's on the board (positive: White is ahead; a piece made by a promotion counts, so it is not "points taken"); `capturedByWhite` is the Black pieces that are gone and `capturedByBlack` the White ones (`Game/CapturedMaterial.h`, position-only: see its line in the layout). **It is derived:** computed from the model's position at every `get_state` call, with no state, no version of its own and no member in `set_state`; the state version already moves with every move, reset and `set_state` that can change it. Decided (the entry left it open): yes, because it is a pure function of the position, costs one JSON member and lets the headless smoke check the feature without a screenshot.
- `analysis` is `{"evaluationOn", "hintRequested", "thinking", "evaluation", "hint", "lines", "ratingsOn", "ratings", "error"}` (`PositionAnalyst`, `src/Chess/Engine/CLAUDE.md`, "The analysis in the game"): the engine the person picked (`opponent.engine`), never handicapped, with the limits of the strongest level (Stockfish 2 s, Own depth 5), in a process of its own. `evaluationOn` is false at the start of every game (it costs CPU, and a process for Stockfish). `hintRequested` is true from the `set_state {"analysis": {"hint": true}}` for the position now on the board until the position changes (a move, a reset, a `set_state` drop it; a hint is asked again by hand). `evaluation` is null while it is off or not yet computed for this very position, else `{"score": {"kind": "centipawns"|"mate", "value": int}, "text": "+0.35"|"#3", "depth": int}` **from White's view** (positive: White is better or mates). `hint` is null until the answer for this position has come, else `{"move": "e2e4", "text", "depth"}` (the score in the side to move's view, as the engine gave it); the move is a listed action and is never played. `lines` is an array, best first, of `{"move", "score": {"kind", "value"}, "text", "depth"}` **from White's view, as `evaluation`** (the analyst asks the engine for two lines, MultiPV; the first is the line of the evaluation and the hint, the second the next best move and how the position stands if it is played; a position with one legal move has one line); it is `[]` unless the evaluation is on or a hint was asked for this position and the answer has come, goes with the hint and the engine pick like them, and nothing is searched only for it (`chess-brilliant-moves` takes the margin between the two lines from it). `error` is null or `{kind, detail}` with the kinds of `opponent.error`; a missing Stockfish is `launch_failed` and nothing falls back to the other engine. A hint is for the person: refused on a side the program plays, so on either turn while two programs play (`not_your_turn`, new in `ChessControlErrors`), on a finished game `game_over`; in a game of two people either side may ask. `list_actions` is unchanged by all of it. A change of `opponent.engine` drops the old engine's answer at once, in the same call. **The ratings of the moves** (`MoveRater`, owned by the analyst; slice 1 of `chess-brilliant-moves`, the mark on the board is slice 2): `ratingsOn` is false at the start of every game (it costs CPU; a reset keeps the switch, like the evaluation's) and `ratings` is an array with one entry per move of `moves`, in the same order (`[]` for no move): `null` while the move is not rated, else `{"brilliant": bool, "reason": "brilliant"|"not_best"|"forced"|"obvious"}`. **The definition:** a move is brilliant when it is the best move of the own engine at depth 5 in the position it was played in (the first of two lines of an analysis of the position BEFORE the move) and it was a choice: `forced` is a position with one legal move, `obvious` one where the second line is 200 centipawns or more behind (a forced recapture, a mate in one), `not_best` is any other move; a tie is a gap of 0, so line 1's move is brilliant. The chess-site meaning (a good sacrifice) is not asked for. It is **always the own engine**, whatever `opponent.engine` is (deterministic: the same game gets the same ratings twice; no process, no Stockfish), with an engine object of its own, in the background, the oldest move first, only while `ratingsOn`; the ratings of earlier moves stay after a new move and go with a reset or a `set_state` of a fen; switching off keeps what is rated. A rating that arrives moves the state version. The rater's failure (an engine that cannot be made, a search that fails) is not in `analysis.error`; it is logged, and the move stays `null`.
- The state version is `ChessGameModel::GetVersion()` plus `OpponentController::GetRevision()` plus `PositionAnalyst::GetRevision()`. It grows on a played move, a reset, a `set_state`, a pick of the side, level or engine, an error that appears or goes, a switch of the evaluation, a hint asked or dropped and an analysis that arrives or fails, not on a selection or on a search that starts or ends (`thinking`). A person's move by mouse and the program's move grow it too, so `state_changed` reports them. It never goes back.
- `list_actions` is unchanged by the opponent: every action is a move, which `tools/stockfish_bridge.py` relies on. `perform_action` is not blocked for the program's side: a controller may play for it (a search that this makes stale is dropped by the version); only the mouse is kept from the program's side.
- The scene follows the model: a move, a promotion, a reset and a `set_state` all show in a `screenshot`, which is how a headless run is checked by eye.

## Rules

Standard chess, Chess960 excluded: legal moves only (pins, check, castling, en passant, promotion), checkmate, stalemate and the draws that end the game by themselves: insufficient material, threefold repetition and 50 moves without a capture or a pawn move. FIDE makes a player claim the last two (it ends a game by itself only at fivefold and 75 moves), but the window has no way to claim, so they apply automatically. Both thresholds are named constants in `GameStatus.cpp`.

- A move is a `Move` from `MoveGenerator::GenerateLegal()`; `ChessGameModel::TryMove()` accepts nothing else and answers `std::expected<void, MoveError>` (`GameOver`, `IllegalMove`). `Position::IsLegal()` assumes a pseudo-legal move from the generator (while in check it relies on the generator having restricted the targets), so do not call it with a hand-made move: parse text with `MoveGenerator::ParseUci()`.
- Castling is the king's move (`e1g1`), as in UCI. A promoting pawn has four moves per target, queen first; a click on the target leaves the promotion pending in the model (`ChessGameModel::HasPendingPromotion()`) and `ChoosePromotion(piece)` plays it (the window's modal `PromotionPanel` makes that call, see "The promotion picker"); `TryMove` / UCI (`e7e8n`) name the piece themselves, as the program and the control API do.
- `Position` keeps the en passant square only when a pawn can capture onto it (so positions that are equal for the rules have equal keys and FEN). `FromFen` rejects positions the rules cannot reach in the ways that would break the lookups: a king count other than one, a pawn on a back rank, more than 16 pieces of one color (the scene has 16 piece nodes per color, so any accepted position can be shown), the side that just moved in check, castling rights without the king and rook in place.
- A finished game accepts no move. The window shows the end with the red king (bright on check, dark on mate), the dimmed board and a bar across it (white, black or gray for a draw); the HUD says who won and why ("White wins", "Checkmate"), and the reason also goes to the log. A click on the board after the end, or the Reset button, starts a new game.
- The magic bitboards are searched for on first use (about 90 ms in a Debug build, measured on macOS) with a fixed seed, every candidate checked against the slow ray walk. If that becomes too slow, print the found numbers once and embed them as constants.

New rule code goes into `Game/` with a gtest case; do not patch around the generator in the model or the components.

## Tests

`tests/`, executable `ChessTests`, plus the control smoke `BagiChessControlSmoke` (`tests/control_smoke.py`) under ctest. What each test file covers, the fake UCI engine and the helpers are in `tests/CLAUDE.md`: read it before adding or changing a test. New rule code goes into `Game/` with a gtest case. Tests that need Stockfish skip themselves without one.
